**Refresh:** the idempotency key and a "claim pending" marker live in sessionStorage, so after a reload the app reads `/me` and, if the offer is still there, finishes the claim once with the same key. **Network drop:** writes retry with the same key (backoff 300 ms to 5 s with jitter, at most 5 tries); a banner says "Reconnecting… your place is safe". **Many tabs:** each tab has its own key; the server gives both the same seat. **Lost response:** the server saved the claim but the answer never arrived; the retry sends the same key and gets the same seat back (tested: two claim requests, one key, one seat).
**Countdowns use server time:** every response has `server_time`; the app keeps a smoothed offset and all timers use `serverNow()`, so a phone with a wrong clock sees the same deadline as everyone.
**Retry table in plain words:** no answer or 502/503/504 → try again, same key, wait longer each time; 429 → wait what the server says, at most twice; `TOKEN_INVALID` → fetch a fresh token from `/me` once, same key; signed out → sign-in screen, pending claim kept; any other 4xx → stop and show it. A retry can only repeat the same action, tries are bounded and spaced, and buttons lock after the first tap, so retrying never makes anyone faster.
