New: `docs/contract/sim-auth-flow.md` (simulator login example, phone range `+91 9xxxxxxxxx`). **Built** (`api/app/identity/`): peppered HMAC phone hash (`phone.py`), Redis OTP store with atomic Lua guess counting and single-use consume (`otp.py`), signed session tokens with server-side 24 h expiry and cached lookup (`session.py`), race-safe user/session upsert (`users.py`), client IP / UA hash (`client.py`), the two flows (`service.py`), real `deps.session_credential`. Migration `20261004100400` swaps the plain `(user_id, device_id)` index for a partial UNIQUE index on live sessions (`WHERE revoked_at IS NULL`).
**Hooks, final signatures** (`api/app/abuse/hooks.py`, no-ops, keyword-only): `otp_request_guard(*, phone_hash: str, phone_prefix: str, device_id: str, client_ip: str) -> None` (L6, may raise `OtpThrottled`); `on_identity_verified(*, user_id: UUID, device_id: str, client_ip: str, ua_hash: str, verify_latency_ms: int) -> None` (L7, evidence only). That folder is Saanvi's lane; the stubs are here because the plan calls them from the auth flow.
**Verify:** `uv run fd test-api` 171 passed (final run); `uv run fd lint` clean; bandit 0 real findings (1 false positive), pip-audit clean. Manual `curl.exe` flow: cookie and bearer both accepted and logged the same `user_public_id`; replayed code 410; re-verify same device returned the same token.
**Measured** (4 uvicorn workers, DB pool 30..30 per worker, Redis timeout 50 ms / required 500 ms, APP_ENV=dev, SIM_MODE=true, Docker Desktop on Windows 11, 16 CPUs, load client in a sibling container): 200 concurrent verifies x 10 rounds = 2000/2000 OK, p95 347-633 ms per round (median 428). Cold pool (`DB_POOL_MIN=2`): round 1 p95 1047 ms with 1 of 200 failing, then clean.
**Found and fixed while measuring:** (1) a 50 ms Redis timeout plus the circuit breaker turned a busy event loop into 503s for every login (159 of 200 in one round); OTP now uses `Cache.run_required` (500 ms, no breaker, sequentially pre-opened connections). (2) Handlers read the global settings, so test overrides were ignored; they now read `app.state.settings`. (3) httpx stalls at 200 concurrent requests, so the benchmark (`api/tests/bench_verify.py`) uses raw sockets for the timed phase.
**Changed from plan:** OTP guess counter increments before the comparison (Lua), so parallel guesses cannot beat the limit of 5; `DEL` result decides the single winner; dedupe key is removed when a request dies; OTP HMAC and session HMAC use separate keys derived from `SESSION_SECRET` and the OTP hash binds request_id and phone_hash; sessions expire server-side (cookie and bearer); `device_id` format (8-128 chars, `A-Za-z0-9._:-`) is checked in the handler so the schema did not change; the OTP is never logged, not even in SIM_MODE; SIM_MODE also keeps the plaintext code so a deduplicated request can still return `dev_otp`; `prod` now refuses `COOKIE_SECURE=false`.
**Security review** (secure-code-guardian rules + security-reviewer pass): no way found to mint two identities for one phone (extensions, `00` prefix, other digit scripts all map to the same hash or are rejected; tested); all SQL parameterised; no secret in logs (test checks raw records for the phone in 7 forms, every OTP, token, signature, session UUID, pepper and secrets).
**Risks / for Plan 13:** (a) anyone who knows a phone can burn its 5 attempts or hold its 30 s dedupe slot with their own device_id, so the owner's verify fails the device check: a targeted nuisance, needs L6 throttling; (b) more than 5 verifies in flight on one request delete it, even a correct one (never two sessions; tested); (c) no rate limits on auth yet (Plans 12/13); (d) if Redis is down when a session is revoked, a stale cache entry can return for up to 60 s; (e) the phone hash is a fast keyed hash: if the pepper and the database both leak, the ~1e9 Indian numbers can be enumerated; (f) default trusted-proxy CIDRs include all private ranges, so a client on the same private network is trusted to set `X-Forwarded-For`; (g) numbers starting 6, 7 or 8 are only partly valid mobiles.
**Next (Plan 05):** use `CurrentSession` from `app.deps`; `Session.sid_hash` is ready for admission tokens (Plan 10); the L3 limiter can call `verify_token` (pure CPU) before any Redis or Postgres work.
